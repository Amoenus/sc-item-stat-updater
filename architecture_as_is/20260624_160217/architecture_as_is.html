  • The project has a real staged pipeline architecture, not a chaotic script pile. The key stages are extract baseline INI, refresh source caches, apply localization updates, and deploy.
  • The architecture boundary is much weaker around generated data ownership than around code imports. The repo stores source outputs, derived outputs, raw graph JSON, DCB cache, XML cache, SCMDB raw JSON, SCMDB derived CSV, and root `global.ini` in overlapping lifecycle states.
  • DataCore cache refresh is the architectural center of gravity: it extracts DCB, expands XML, builds a record graph, extracts raw fact CSVs, then scrapes item type CSVs. This is a pipeline inside the pipeline.
  • “Normalization” is partial. Many DataCore extractors use the record graph for discovery/relationships, but then reread XML by path. The graph is both normalized index and giant cache artifact, not a complete normalized source model.
  • SCMDB is described as retired or temporary, yet the workflow still refreshes SCMDB by default for full source refresh, selects SCMDB and DataCore latest directories independently, and retains mining-journal fallback behavior.
  • Mappings are legacy but still structurally present: 23 SPViewer-named mapping JSON files remain, and update planning still has SPViewer key-resolution machinery.
  • Presentation code owns real operational topology: DataCore raw fact groups, concurrency, and item type groupings live in `src/presentation/datacore-task.ts`, not only in application/use-case code.
  • The architecture guard passing is meaningful but narrow. It proves a few import/progress-renderer boundaries, not cache correctness, generated output coherence, source version alignment, or data remapping stability.

Representative Flows

1. Full Pipeline

  • Path: CLI pipeline.ts -> fresh global.ini extraction -> source cache refresh -> batch update -> deploy.
  • Reads/writes: reads game files and source outputs; writes repo global.ini; may write DataCore/SCMDB outputs; may deploy into game folder.
  • Critical observation: update stage hardcodes provider datacore, but source refresh defaults to both DataCore and SCMDB. This is a transitional architecture, not a clean single-provider flow.
  • Confidence: High; direct code evidence.

2. DataCore Cache Refresh

  • Path: prepare -> ensure XML cache -> prepare record graph -> extract raw facts -> finalize raw facts -> scrape item type CSVs -> reconcile classes -> finalize.
  • Reads/writes: reads local Data.p4k, DCB cache, XML cache, graph, XML records; writes graph and dozens of CSVs.
  • Critical observation: this is a multi-stage data warehouse build inside a repo-local `csv/` tree. Cache invalidation uses version tags, DCB metadata/fingerprints, XML counts, and graph existence, but those are spread across use-case logic rather than a single cache manifest/owner.
  • Confidence: High; direct code and recent successful `cache:datacore` run evidence from prior work.

3. SCMDB Bridge Refresh

  • Path: select SCMDB version -> fetch merged/mining/crafting/MEMA JSON -> write raw JSON -> validate -> write mission/contracts/mining/journal/MEMA CSV outputs.
  • Reads/writes: network JSON reads, repo-local raw JSON snapshots, repo-local derived CSV files.
  • Critical observation: the bridge persists both raw and derived data, and derived outputs are still discoverable by normal update-category machinery. Retiring a bridge requires code, docs, generated files, diagnostics, and source listing to move together.
  • Confidence: High.

4. Localization Update

  • Path: prepare latest DataCore and SCMDB dirs -> load dynamic item configs -> preflight declared files/raw facts -> backup -> category updates -> extra steps.
  • Reads/writes: reads CSV/JSON source files, existing INI, optional mapping files; writes patch applications to global.ini and may update mappings for legacy resolution.
  • Critical observation: update planning has reasonable abstractions, but source contract enforcement lives across item configs, preflight, source diagnostics, and command inventory. The source contract is distributed, not centralized.
  • Confidence: High.

Architecture Sensibilities Audit

1. The Pipeline Is Conceptually Clean, But Operationally Nested

Observed: docs describe acquisition -> normalization -> planning -> application -> deployment. Code mostly follows that at the top level. But DataCore refresh itself contains a second pipeline with its own caches, graph, raw facts, derived facts, item outputs, class reconciliation, and task topology.

Implication: the architecture has two levels of pipeline, but only one level is documented as architecture. The DataCore sub-pipeline is too important to remain a use-case implementation detail.

2. Cache Boundaries Are Physical, Not Semantic

Observed: DCB cache, XML cache, record graph, raw fact CSVs, item CSVs, SCMDB raw JSON, SCMDB derived CSV, and root INI outputs all live under ordinary repo paths. The latest inventory found 12.8 GB under `.xmlcache`, 1.2 GB under `.dcbcache`, 358 MB under latest DataCore outputs, and 23 MB under latest SCMDB outputs.

Implication: “cache” is not consistently distinguished from “generated source output” or “reviewable artifact.” That raises the cost of cleanup, churn review, version migration, and accidental commits.

3. Normalization Does Not Fully Normalize

Observed: DataCore graphing extracts record metadata, localization references, and GUID indexes, but raw fact and item extractors still read XML files directly by graph path. Recent graph memory work also introduced compact graph modes, which means the graph has multiple fidelity levels.

Implication: the graph is not a stable normalized model; it is an index plus selected projections. That is not wrong, but it should be named and managed as an index. Calling it normalized source data would overstate it.

4. SCMDB Retirement Is Real But Not Finished

Observed: provider matrix says categories are DataCore primary, while SCMDB audit still identifies mining-journal fallback, and batch mode still describes DataCore + SCMDB. Full source refresh defaults to both sources unless cached or narrowed.

Implication: the migration has progressed, but labels now risk outrunning reality. The architecture needs a more explicit bridge lifecycle: active, optional fallback, diagnostic only, retained historical, deleted.

5. Mapping And Remapping Logic Is Spread Across Four Places

Observed: mapping files live under mappings/; mapping-store loads/saves JSON; key resolver maps names to localization keys; item configs provide getTargetKeys, alternate desc keys, custom source loaders, and source file declarations.

Implication: the mental model for “how does a row become an INI key?” is not singular. It is a chain: generated CSV shape -> category config -> optional source loader -> target-key remapper -> existing INI resolver -> optional mapping persistence. This is where subtle drift will hide.

6. Presentation Owns Too Much Workflow Shape

Observed: datacore-task.ts defines raw fact groups, item type groups, and concurrency. The application plan exposes stages, but the grouping topology lives in presentation.

Implication: CLI UX and operational execution are entangled. If another runner or CI summary needs the same topology, it either imports presentation concepts or duplicates group knowledge.

7. There Are Real Guardrails And Tests

Observed: architecture guard passed; 109 test files exist; tests cover DataCore scrape behavior, graph records, pipeline flags, source preflight, and presentation task behavior.

Implication: this is not an ungoverned codebase. The weakness is not lack of care; it is that the guarded boundaries are narrower than the actual architectural risk surface.

Test Suite Interpretation

  • Framework: Node built-in test runner via node --import tsx/esm --test src/**/*.test.ts.
  • Observed coverage shape: 109 test files. Strong targeted tests exist for DataCore scrape behavior, record graph relationships, pipeline/cache command rendering, preflight source validation, generated strings, and update planning.
  • What tests prove well: many edge-case extractors and key-mapping behaviors are encoded as regression tests; preflight explains missing source files with provider/channel context; presentation tests cover nested task rendering and concurrency assumptions.
  • What tests do not prove from this audit: full real-data pipeline memory budget, long-running cache invalidation correctness, exact generated-data commit policy, or that all source version combinations are coherent.
  • Commands run: npm run check:architecture passed; npm run typecheck passed. Full npm test was not run in this architecture audit.

Architecture Observations

Observed

  • Top-level pipeline structure exists and is coherent.
  • DataCore source refresh is a large stateful sub-pipeline with its own artifacts and concurrency.
  • SCMDB bridge artifacts still exist and are refreshed by default in full source-cache mode.
  • Legacy SPViewer mapping files and resolver code remain.
  • Generated-data footprint is enormous relative to the codebase.

Inferred

  • The system has migrated from source-provider comparison toward DataCore-first, but older provider abstractions remain because they still solve mapping and bridge problems.
  • Most fragility is no longer in formatting `global.ini`; it is in keeping source artifacts, version folders, graph fidelity, and category source contracts coherent.

Unknown

  • Which generated/cache folders are intended to be committed versus local-only. The worktree currently contains large untracked 4.8.2 outputs and caches.
  • Whether full `npm test` passes after the current dirty changes.
  • Whether source refresh should ever run SCMDB by default once DataCore categories are primary.
