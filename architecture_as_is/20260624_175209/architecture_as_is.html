Executive Summary

Observed: the architecture has materially stronger boundaries than the prior roadmap baseline. DataCore is the default cache source, SCMDB refresh is explicit, generated-data ownership is documented and guarded, active category source contracts are centralized, and SPViewer mapping use is gated behind explicit legacy opt-in.

Inferred: the main remaining risk is no longer a missing policy boundary; it is responsibility concentration. The DataCore scrape use case and its test suite are very large, update planning still owns source loading plus legacy mapping mechanics plus preflight, and generated-data retention is documented but not yet enforced as a pruning workflow.

Findings

ObservedHigh DataCore scrape is still a responsibility hotspot

src/application/use-cases/run-datacore-scrape.ts is 3937 lines and imports acquisition, XML parsing, graph building, metadata validation, raw fact extraction, item type extraction, SCMDB component fallback, and plan construction. Its test file is 4563 lines.

Risk: correctness work around graph fidelity, cache metadata, or raw fact extraction has a large blast radius. The next cleanup should extract cache metadata, graph preparation, raw fact stage runners, and item-type stage runners into modules that keep createDataCoreScrapePlan as the orchestration facade.

ObservedMedium Update planning mixes current source contracts with legacy mapping mechanics

src/application/update/update-planning.ts owns source data loading, source-file preflight, localization key validation, SPViewer lookup loading, and update plan construction. Separately, build-patch-plan.ts now rejects legacy SPViewer key resolution unless legacyKeyResolution is passed.

Risk: legacy mapping paths remain physically near normal update planning. A cleaner layout would isolate SPViewer mapping resolution behind a legacy adapter module and keep the active update planner focused on provider-resolved rows and localization patch decisions.

ObservedMedium Generated-data retention is documented but not automated

DataCore contains active caches plus four version output directories; SCMDB contains three version directories. docs/generated-data-ownership.md classifies old version directories as obsolete historical output unless explicitly pinned.

Risk: old outputs are easy to misread as active comparison baselines, especially when DataCore and SCMDB versions diverge independently. A dedicated retention report or guard should identify current selected versions, explicitly pinned versions, and removable historical directories.

ObservedMedium Historical SPViewer mappings are fenced but still unresolved inventory

The repo still contains 22 mappings/*.spviewer.json files. Documentation classifies them as historical legacy mappings, and architecture checks reject active category configs that use nameColumn, lookupCsvFile, or .spviewer. sources.

Risk: the drift surface is controlled, not eliminated. The next step is a named audit that either ties each mapping file to a retained historical diagnostic or removes it in a dedicated cleanup commit.

ObservedMedium Source contract consolidation is real but has parallel consumers

category-source-contracts.ts now feeds listing, diagnostics, and preflight behavior, and architecture checks ensure active configs declare auditable source files. Related consumers still format and interpret those contracts in category-listing.ts, source-freshness-diagnostics.ts, scmdb-dependency-audit.ts, and update-planning.ts.

Risk: provider labels and optional/fallback wording can drift across output surfaces. Prefer one formatted source-contract projection that diagnostics, category listing, and preflight can share.

ObservedMedium Mission and DataCore type files carry config/data/build logic together

src/items/missions/mining-locations.ts is 1191 lines, src/items/missions/datacore-descriptions.ts is 772 lines, and src/sources/datacore/types.ts is 819 lines.

Risk: these files may be stable, but they are harder to review and invite duplicated local helpers. Split by domain role when the next functional change touches them: source declarations, row transforms, constants, and exported category config should be separate where practical.

InferredMedium Historical documentation can read as current state

Current docs such as docs/generated-data-ownership.md and docs/source-hierarchy-and-scmdb-audit.md describe the post-roadmap boundaries clearly. Older planning and functional docs still contain historical SPViewer/SCMDB statements that may be useful as audit history but unsafe as current architecture references.

Recommendation: add status headers or an index that marks current ADR/PRD/report docs versus historical notes.

Duplication and Drift Read

Observed duplication is mostly semantic rather than literal: multiple modules need to describe "which source file belongs to which provider" and "is this fallback optional or active." The new source-contract module and architecture guardrails reduce that drift, but the remaining duplication is in presentation and diagnostic formatting, not in the underlying provider inference.

Mapping mismatch/drift is currently contained by policy and guardrails. The repo still retains historical mapping files, but active DataCore and mission configs are guarded away from SPViewer mapping fields.

Recommended Next Slices

  1. Extract run-datacore-scrape.ts into focused application modules while preserving createDataCoreScrapePlan as the stable interface used by presentation.
  2. Add a generated-data retention report that classifies current, pinned, historical, rebuildable-cache, and removable paths before any pruning happens.
  3. Audit all 22 mappings/*.spviewer.json files and mark each as diagnostic, historical-retained, or removable according to the ownership policy.
  4. Extract legacy SPViewer key resolution out of active update planning into a legacy adapter module with narrow tests around explicit opt-in.
  5. Consolidate formatted source-contract projections so category listing, preflight, source freshness, and SCMDB dependency audit share labels and optional/fallback semantics.
  6. Add documentation status markers so ADR/PRD/current architecture reports are clearly separated from historical audit notes.

Open Risks

  • Broad npm test has a known Node/Piscina native-loader crash in previous runs; this report did not rely on a full test pass.
  • Generated-data pruning was intentionally not performed during this reporting pass.
  • No dynamic pipeline execution was performed; flow claims are static observations from code paths and guardrail checks.
